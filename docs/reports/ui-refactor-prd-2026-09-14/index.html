Product requirements and refactor plan

A luminous workbench for dynamical systems.

The approved light scientific workbench is now implemented as the production baseline for Solver and Viewer. This report is the product-requirements record, implementation map, before/after evidence, and acceptance ledger for continued refinement.

Status: implemented baseline Default: light scientific theme Target: WCAG 2.2 AA Architecture: native Win32/GDI+
00

Recommendation at a glance

Refactor the shared visual language first, then reorganize each workbench around its primary task. Preserve every scientific and archive boundary.

Light is the defaultPale blue-gray canvas, white working surfaces, navy text, restrained scientific color.
One focal taskSolver culminates in review/run. Viewer culminates in the active scientific figure.
Context stays nearbySelection identity, provenance, validation, and actions move beside the work they explain.
Progressive disclosureFrequent controls stay visible; rare archive/file actions move into compact menus or drawers.

The current palette has respectable nominal contrast, but perceived visibility is reduced by a nearly black shell, weak separation among dark surfaces, dense horizontal chrome, and a jarring transition to white plots. The answer is not merely brighter cyan. It is a coherent light surface hierarchy with fewer simultaneous choices.

Before-state evidence

The Viewer image was painted by the installed native workbench’s hidden capture path against the real archive. The Solver image is retained native render evidence from 6 September and is cross-checked against the current theme and layout source.

Viewer: current installed workbench

1 Seven equal-weight header actions flatten priority.
2 Inspector consumes the upper half of the navigation rail.
3 Workspace, view, page, drag, coordinate, and scale controls form several competing rows.
4 The tree is structurally good but vertically constrained and visually low-energy.
5 White plots are clear in isolation but visually detach from the nearly black workbench.

Solver: current native system panel

1 The proposed-job tree is useful, but its selection and action hierarchy compete with the editor.
2 Utility actions span the header with little frequency-based grouping.
3 System/preset and mode navigation do not establish a strong task sequence.
4 The parameter book is information-rich but clipped/dense at common widths.

What should remain

Product knowledge
  • Native controls, DPI-aware metrics, and asynchronous work.
  • Solver job hierarchy and Viewer's provenance-backed data tree.
  • White scientific plots and precise mathematical typesetting.
  • Separate Solver/Post-processor and Viewer executable responsibilities.
  • Resizable panes and immutable archive behavior.

What should change

Presentation debt
  • Dark-by-default shell and weak dark-surface differentiation.
  • Equal visual weight for primary and rare actions.
  • Inspector/tree competition and repeated context.
  • Large multi-row toolbar footprint in Viewer.
  • Small targets, understated focus, clipping, and missing state standards.

04

Information architecture

Rearrangement is intentionally a presentation refactor. It does not alter job JSON, numerical services, archive identity, or the scientific tree model.

Current shell

  • Many global actions in one horizontal strip
  • Navigation / editor / inspector all permanently visible
  • Settings grouped mostly by implementation surface
  • Status, progress, and validation separated from next action
TreeEditor + toolbarsInspector / output
→

Proposed shell

  • App mode and identity in header
  • Contextual actions beside current object
  • Frequent task sequence in center workspace
  • Review/provenance rail collapses at constrained widths
ExplorerFocused scientific workContext / review

Solver task model

Configure → validate → run
  • Application modes: Solve and Post-process.
  • Setup stages: System, ICs, Control, Integrator, Review.
  • Job hierarchy remains the left source of scope and ownership.
  • Validation summary and execution output share the right review rail.
  • Plan and Run & archive remain visible in one sticky action area.

Viewer task model

Orient → inspect → compare/export
  • Data tree receives most of the left rail by default.
  • Inspector becomes a resizable Details/Lineage drawer below the tree.
  • Selected-object breadcrumb and short label lead the center workspace.
  • View, workspace, plot manipulation, scale, and coordinates become one compact contextual bar.
  • Rare export/help actions move to a stable utility group.

08

Refactor plan

The implementation followed these separable work packages. Foundation, shared shell, Solver staging, and Viewer hierarchy are delivered here; deeper control consolidation, external UIA review, and moderated usability remain incremental follow-ups.

PR 1 · Evidence and semantic tokens Delivered

Freeze current screenshots and interaction inventories. Introduce a versioned light token set, text tiers, control tokens, focus colors, density metrics, and contrast tests behind the shared theme API.

  • Primary files: Theme.hpp/.cpp, native UI tests, UI system documentation.
  • Implemented as the production light baseline.

PR 2 · Shared accessible primitives Delivered baseline

Refactor owner-drawn buttons, folder tabs, combo boxes, scrollbars, splitters, tooltips, progress, and inline fields to consume tokens and expose complete states/UIA metadata.

  • Windows-native focus, selection, popup lists, and DPI behavior retained.
  • External assistive-technology auditing remains a follow-up.

PR 3 · Shared shell and responsive pane policy Delivered baseline

Separate app-mode, contextual, and utility actions; add consistent breadcrumbs/context headers; implement wide/compact/narrow layouts and collapsible context rails.

  • Solver's three-pane and Viewer's two-pane ownership models remain intact.
  • Rare-action overflow consolidation remains an optional refinement.

PR 4 · Solver workflow projection Delivered baseline

Map existing controls into five setup stages, reflow parameter families, establish the right review rail, and make Plan / validate plus Run & archive the persistent culmination.

  • SolveJobModel, job JSON, execution pane, controller and IC dialogs are unchanged.
  • Validation-to-field deep linking remains a refinement.

PR 5 · Post-processor projection Theme delivered

Apply the lighter shell and form hierarchy to source selection, pipeline staging, method-specific editors, and planning/execution while preserving every parity-ledger capability.

  • Shared theme and shell are delivered.
  • Deeper method-editor rearrangement remains a focused follow-up.

PR 6 · Viewer context and toolbar Hierarchy delivered

Allocate the rail to the tree first, convert Inspector to Details/Lineage drawer, add selected-object context, and consolidate plot controls without changing the tree's scientific grouping or leaf-only sorting.

  • Panel composition, workspace state, KROM layout, observables scrolling, and phase context are retained.
  • Tree sorting and selected context are delivered; further plot-toolbar compression remains optional.

PR 7 · Accessibility, DPI, performance and rollout In validation

Run complete keyboard/UIA, contrast, target-size, DPI, background-render, repaint, scroll, and package-install gates. Compare before/after task walkthroughs with a scientist.

  • Light is now the default; automated contrast and hidden workbench checks are delivered.
  • External UIA/DPI matrix and moderated task review remain before declaring the design final.

Solver

  • Find and edit a physical parameter.
  • Plan without executing and resolve one error.
  • Run, interpret progress, and cancel safely.
  • Open a trajectory in Viewer.

Viewer

Orientation + discovery
  • Find the newest forced training set.
  • Switch to phase context and locate IC/EC.
  • Add and rearrange a plot panel.
  • Compare two compatible records.
